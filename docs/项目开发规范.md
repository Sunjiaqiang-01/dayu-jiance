## 一、核心原则（强制执行）

### 1.1 UI/UX组件规范

```
┌─────────────────────────────────────────────────────────────────────┐
│                         组件获取铁律                                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ⚠️  所有UI组件必须使用 21st-dev-magic 工具查询获取！               │
│                                                                     │
│  ⚠️  禁止手动编写组件代码！                                         │
│                                                                     │
│  ⚠️  禁止因为实现复杂、困难就删减组件或改变样式！                    │
│                                                                     │
│  ⚠️  必须100%像素级复刻设计稿！                                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 禁止事项

| 禁止项 | 原因 | 替代方案 |
|--------|------|----------|
| ❌ 手动编写组件代码 | 质量无法保证 | 使用21st-dev-magic获取 |
| ❌ 简化复杂组件 | 破坏用户体验 | 想办法实现或求助 |
| ❌ 替换为更简单的组件 | 降低产品质量 | 坚持原设计 |
| ❌ 删除动画效果 | 失去专业感 | 必须保留 |
| ❌ 使用Ant Design替代shadcn/ui | 技术栈不统一 | 坚持使用shadcn/ui |
| ❌ 跳过组件获取流程 | 违反规范 | 必须按流程执行 |

## 二、组件获取标准流程

### 2.1 六步执行流程

```
步骤1️⃣ ：确定组件需求
    │
    │ 明确需要什么组件
    │ 如：环形图、进度条、选择卡片、条形图等
    │
    ↓
步骤2️⃣ ：21st-dev-magic 查询
    │
    │ 使用 21st_magic_component_inspiration 工具
    │ 搜索关键词：组件类型 + 使用场景
    │ 示例：搜索 "pie chart donut chart analytics percentage"
    │
    ↓
步骤3️⃣ ：选择最佳组件
    │
    │ 根据设计风格选择最匹配的组件
    │ 考虑：样式、动画、交互、代码质量
    │ 选择后复制组件代码
    │
    ↓
步骤4️⃣ ：获取生产级代码（如需要）
    │
    │ 使用 21st_magic_component_builder 工具
    │ 获取完整的、可直接使用的组件代码
    │
    ↓
步骤5️⃣ ：集成到项目
    │
    │ 将组件代码放入 src/components/ui/ 对应目录
    │ 遵循项目文件命名规范
    │
    ↓
步骤6️⃣ ：适配定制
    │
    │ 根据业务需求调整样式和交互
    │ 保持设计规范不变
    │ 如需大改，寻求上级确认
    │
    ↓
    ✅ 完成
```

### 2.2 常用组件查询关键词

## 五、技术栈强制规范

### 5.1 前端技术栈

| 层级 | 技术选型 | 禁止使用 |
|------|----------|----------|
| UI组件库 | **shadcn/ui** | ❌ Ant Design |
| CSS框架 | **Tailwind CSS** | ❌ styled-components |
| 图表库 | **Recharts + 自定义** | ❌ ECharts（除非必要） |
| 动画库 | **Framer Motion** | ❌ CSS动画（复杂场景） |
| 状态管理 | React Context / Zustand | 避免Redux过度设计 |

### 5.2 代码规范

```typescript
// ✅ 正确：使用 cn() 工具合并类名
import { cn } from "@/lib/utils"

const Button = ({ className, ...props }) => (
  <button className={cn(
    "inline-flex items-center justify-center",
    "rounded-md text-sm font-medium",
    "transition-colors focus-visible:outline-none",
    className
  )} {...props} />
)

// ❌ 错误：手动拼接类名
const Button = ({ className, ...props }) => (
  <button className={"inline-flex items-center justify-center rounded-md text-sm font-medium " + className} {...props} />
)
```

## 七、质量检查清单

每个功能开发完成后，必须检查以下项目：

```
□ 组件是否使用21st-dev-magic获取？
□ 组件样式是否100%匹配设计稿？
□ 动画效果是否完整保留？
```

## 八、常见问题与解答

### Q1: 21st-dev-magic找不到合适的组件怎么办？

**A**: 
1. 尝试不同的搜索关键词
2. 搜索更通用的关键词（如只用"chart"而不是"donut chart"）
3. 查询相邻类型的组件（如查"progress"而不是"step progress"）
4. 如果确实找不到，在团队群里讨论解决方案

### Q2: 组件实现太复杂，难度很高怎么办？

**A**:
1. 首先尝试分解任务，分步骤实现
2. 查看组件文档和示例代码
3. 在团队群里寻求帮助
4. **绝对不能简化设计或删除组件**

### Q3: 设计稿和获取的组件有差异怎么办？

**A**:
1. 以设计稿为准，调整获取的组件代码
2. 保持核心功能和交互不变
3. 如需大幅调整，寻求设计师确认

### Q4: 可以自己手写简单的组件吗？

**A**: 
- **基础组件**（如简单的div、span）：可以手写
- **复杂组件**（如图表、进度条、选择器）：**必须使用21st-dev-magic获取**
- **不确定时**：优先使用21st-dev-magic

## 九、违规处理

### 9.1 违规类型

| 违规类型 | 示例 | 处理方式 |
|----------|------|----------|
| 严重违规 | 手动编写核心业务组件代码 | 代码回退 + 重新实现 |
| 一般违规 | 简化了动画效果 | 补充完善 |
| 轻微违规 | 文件命名不规范 | 改正命名 |

### 9.2 处理流程

```
1. 发现违规 → 通知开发者
2. 评估影响 → 确定处理方式
3. 执行修复 → 按照规范改正
4. 复核确认 → 确保符合标准
```
